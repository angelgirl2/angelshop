# گزارش تغییرات نسخه تولیدی Angel Shop

## تغییرات در این بسته

1. بک‌اند جدید مستقل در `cloudflare-production/` با Cloudflare Worker + D1 ساخته شد؛ به KV قبلی متصل نیست.
2. ساختار D1 برای کاربر، نشست، کاتالوگ، سبد، سفارش، اقلام سفارش، تاریخچه وضعیت، تنظیمات و rate limit اضافه شد.
3. ذخیره رمز با PBKDF2-SHA256 و salt تصادفی، ذخیره hash توکن، انقضای نشست و پاک‌سازی زمان‌بندی‌شده پیاده‌سازی شد.
4. موجودی محدود از طریق trigger دیتابیس هنگام ثبت سفارش رزرو و هنگام رد سفارش آزاد می‌شود. trigger مانع oversell در رقابت هم‌زمان سفارش‌ها است.
5. ثبت سفارش ابتدا در D1 انجام می‌شود و سپس پیام به بله ارسال می‌شود؛ خطای شبکه بله باعث از دست رفتن سفارش نمی‌شود.
6. API سبد خرید سمت سرور اضافه شد و برنامه سبد را پس از ورود همگام می‌کند.
7. توکن ورود برنامه از SharedPreferences به flutter_secure_storage منتقل شد؛ مقادیر قدیمی plaintext فقط از کلیدهای مربوط به احراز هویت پاک می‌شوند.
8. URL سرور از طریق `--dart-define=API_URL` تنظیم می‌شود و مقدار نمونهٔ پیش‌فرض حذف شد.
9. ارتباط HTTP ناامن در Android غیرفعال شد.
10. Release دیگر به‌صورت پنهانی با Debug keystore امضا نمی‌شود؛ وجود key.properties و JKS واقعی الزامی است.
11. مسیر و فایل‌های legacy حفظ شده‌اند؛ استقرار جدید فقط از `cloudflare-production/` انجام می‌شود.

## نکته پلن Cloudflare

احراز هویت با PBKDF2-SHA256 و ۱۲۰هزار تکرار طراحی شده است. سقف CPU پلن Workers Free برابر ۱۰ms برای هر درخواست است. تست محلی Node زمان سپری‌شدهٔ WebCrypto را حدود ۲۷ms نشان داد، اما این عدد اندازه‌گیری CPU در runtime کلودفلر نیست؛ بنابراین باید پس از استقرار ثبت‌نام/ورود در داشبورد همان حساب از نظر CPU بررسی شود. در صورت عبور از سقف، Workers Paid/Standard لازم است؛ تعداد دورهای هش برای دور زدن محدودیت کاهش داده نشده است.

## اعتبارسنجی انجام‌شده

- `node --check` روی Worker موفق شد.
- مسیر import کاتالوگ با secret در هدر به‌جای URL محافظت می‌شود.
- شناسه سفارش به ۴۸ بیت entropy افزایش داده شد و رویداد تغییر وضعیت تکراری محدود شد.
- migration با SQLite اجرا شد.
- سناریوی رزرو موجودی و آزادسازی موجودی در رد سفارش با SQLite آزمایش شد.
- محیط حاضر Flutter/Dart SDK و Wrangler احراز‌شده ندارد؛ بنابراین build واقعی APK و deploy واقعی Cloudflare از این محیط قابل تأیید نبود.

## موارد نیازمند حساب/اطلاعات مالک

- ورود OAuth به Cloudflare و تأیید ایجاد Worker و D1
- توکن ربات بله و شناسه چت مدیر برای اعلان‌های بله
- JKS نهایی و رمزهای آن برای ساخت APK امضاشده
- پنل پیامک/درگاه پرداخت/اطلاعات ارسال در صورت نیاز به تأیید شماره و فروش با پرداخت آنلاین

## حفاظت از داده و استقرار

- اسکریپت `cloudflare-production/backup-d1.ps1` خروجی SQL از D1 راه‌دور می‌گیرد و هیچ داده‌ای را حذف نمی‌کند.
- استقرارهای خودکار GitHub فقط روی شاخه `production-ready` اجرا می‌شوند؛ `main` در این بسته عمداً trigger نشده است.
- کلید امضای Android و `key.properties` واقعی از بسته حذف شده‌اند؛ نمونه امن `android/key.properties.example` باقی است.
- ورودی واردسازی کاتالوگ با هدر `X-Setup-Secret` محافظت می‌شود؛ secret در URL واردسازی قرار نمی‌گیرد.
- محدودسازی تلاش ورود با UPSERT اتمیک انجام می‌شود تا درخواست‌های هم‌زمان شمارنده را از بین نبرند.

## آزمون‌های نهایی این بسته

- سینتکس JavaScript فایل Worker با Node.js بررسی شد.
- فایل‌های YAML مربوط به GitHub Actions با parser بررسی شدند.
- migration روی SQLite اجرا شد؛ سناریوی موجودی ناکافی، rollback سفارش، رزرو موجودی و بازگشت موجودی پس از رد سفارش آزمایش شد.
- منطق UPSERT محدودسازی ورود به‌صورت اتمیک روی SQLite آزمایش شد.
- فهرست ۳۴ محصول معتبر است و لینک تمام تصاویر فهرست HTTPS است.
- فایل ZIP از نظر نبودن `android/key.properties` واقعی و فایل JKS بررسی شد.

## مواردی که در این محیط قابل اجرا/تأیید نبودند

- Flutter/Dart SDK و PowerShell در محیط ساخت موجود نبودند؛ بنابراین APK نهایی، اجرای `flutter pub get` و parse/اجرای واقعی اسکریپت PowerShell تأیید نشده‌اند.
- حساب Cloudflare از ابزارهای این گفتگو قابل ورود مستقیم نیست؛ در نتیجه Worker/D1 واقعی هنوز در حساب کاربر ساخته یا deploy نشده‌اند. اجرای `deploy.ps1` روی Windows و تأیید OAuth، مرحلهٔ الزامی مالک حساب است.
- GitHub مخزن یا شاخه اصلی ویرایش نشده است. بسته آماده است تا کاربر پس از استقرار اولیه، آن را روی شاخه جداگانه `production-ready` قرار دهد.
- آزمون end-to-end روی D1 راه‌دور و Worker واقعی بعد از deploy باید انجام شود.
